# Публикация на GitHub

Рекомендуемое имя репозитория: **robloxgang-utilities**.

Описание: `Fabric client utilities: sneak mode hotkey, hourly :52 reminder and RobloxGang name colors.`

Темы: `minecraft`, `fabric`, `minecraft-mod`, `client-side`, `java`.

## 1. Загрузить исходники

Создайте пустой репозиторий на своём GitHub-аккаунте. Выберите публичность самостоятельно. Не добавляйте через форму GitHub дополнительные README или LICENSE: они уже включены.

Распакуйте подготовленный архив исходников и откройте терминал в папке проекта. Замените `OWNER` на имя своего аккаунта или организации:

```sh
git init -b main
git add .
git commit -m "Prepare RobloxGang Utilities 1.1.2"
git remote add origin https://github.com/OWNER/robloxgang-utilities.git
git push -u origin main
```

Если Git попросит имя и email автора коммита, задайте свои данные обычными настройками Git. Не добавляйте в репозиторий архивы релиза, мир тестового сервера или папки Gradle: правила исключения включены в `.gitignore`.

## 2. Проверить GitHub Actions

После push откройте **Actions → Build and test**. Workflow читает `versions.json`, использует JDK 25, собирает семь отдельных вариантов, запускает unit-тесты, проверяет содержимое JAR и сохраняет артефакты `mod-<Minecraft>`.

Первый запуск GitHub CI ещё нужно выполнить в вашем репозитории. Локальная проверка workflow и предыдущие игровые прогоны не являются результатом запуска на hosted runner.

Для локальной сборки нужны PowerShell 7 и JDK 25:

```powershell
./build-all.ps1
```

JAR и контрольные суммы появятся в `dist/1.1.2/`. В репозитории версия читается из `gradle.properties`, поэтому менять имя JAR вручную в скриптах не нужно.

## 3. Создать черновик релиза

После успешной проверки main создайте тег на проверенном коммите:

```sh
git tag -a v1.1.2 -m "RobloxGang Utilities 1.1.2"
git push origin v1.1.2
```

Workflow **Draft GitHub Release** проверит совпадение тега с `mod_version`, повторит сборку через общий CI, соберёт ровно семь JAR, создаст контрольные суммы и загрузит их в **черновик** релиза. Используется стандартный `GITHUB_TOKEN`; отдельный personal access token не нужен.

Откройте **Releases**, проверьте описание и восемь вложений, затем нажмите **Publish release**. Сам workflow не публикует релиз окончательно. При повторном запуске он может обновить существующий черновик, но откажется заменять вложения уже опубликованного релиза.

Для ручного повторного запуска workflow выберите именно тег `v1.1.2` в поле **Use workflow from**, а не ветку main. Это гарантирует, что исходники, бинарные файлы и описание относятся к одному коммиту.

## Альтернатива: загрузить уже подготовленные JAR

Рядом с исходниками подготовлен отдельный архив вложений релиза. Если хотите выпустить именно локально проверенные бинарные файлы, сначала отключите workflow **Draft GitHub Release** в Actions, чтобы он не создавал второй набор вложений. Затем создайте GitHub Release вручную на теге `v1.1.2`, вставьте текст `releases/1.1.2.md` и приложите семь JAR вместе с их `SHA256SUMS.txt`. Это альтернативный способ выпуска; при использовании автоматического workflow локальные вложения загружать не нужно.

Не смешивайте вложения разных сборок. Файл `verification.json` фиксирует контрольные суммы исходных локальных JAR; новая CI-сборка генерирует собственный `SHA256SUMS.txt`.

Лицензия проекта уже указана как MIT. URL репозитория и контакты в метаданных мода можно добавить после создания репозитория; вымышленные ссылки в проект не вставлены.
